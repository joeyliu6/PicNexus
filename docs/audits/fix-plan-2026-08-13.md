## 批次 1：文档修复数据安全（P0，先修——唯一会永久丢用户数据的模块）

### 1.1 修复 Windows `\\?\` 路径前缀导致备份平铺 + 同名备份互相覆盖【高危】

- **问题（大白话）**：文件夹模式下 Rust 扫描返回的路径带 `\\?\` 前缀，前端算相对路径永远对不上（`computeRelativePath` 兜底退化为纯文件名），所有备份挤进一个平面目录；两个子目录里的同名文件备份互相顶掉，撤销时把同一份内容写进两个文件——其中一个的原始内容永久丢失。
- **位置**：
  - 根因：`src-tauri/src/commands/md_scanner.rs` 中 `std::fs::canonicalize`（约 L152、L485 两处）返回 verbatim 路径。
  - 受害端：`src/composables/md-rescue/useFileBackup.ts` 的 `computeRelativePath`（约 L52-61，兜底分支在 L59）。
- **修法**：
  1. Rust 侧统一剥掉 verbatim 前缀（`\\?\` 与 `\\?\UNC\`）再返回前端——可用 `dunce` crate 的 `canonicalize`（引入前先查其文档确认行为），或手工 strip。这是根因修法，一处改、所有消费端受益。
  2. 前端 `computeRelativePath` 增加防御：前缀比对前统一分隔符、Windows 下大小写不敏感比较。
  3. 兜底分支（前缀仍对不上时）改为 **path hash 前缀 + basename**——同文件 L159-161 多文件拖入模式已有现成写法，照抄即可，彻底消灭同名覆盖。
- **验收**：
  - 单测（补进 `tests/unit/composables/md-rescue/useFileBackup.spec.ts`）：folder 为 `\\?\C:\docs`，文件 `\\?\C:\docs\a\README.md` 与 `\\?\C:\docs\b\README.md` → 两个备份路径不同且保留子目录结构。
  - Rust 单测：`scan_md_folder` 返回路径不含 `\\?\` 前缀。
  - 手测：两个子目录各放一个含失效链接的同名 `README.md` → 文件夹模式修复 → 检查 `.picnexus-backup` 目录结构 → 撤销 → 逐字比对两文件内容无互串。

### 1.2 扫描排除 `.picnexus-backup` 备份目录【中高】

- **问题（大白话）**：备份目录建在被扫描文件夹内部，下一轮扫描把"修复前的原件"当正常文档又修一遍——失效数虚高、备份被改写、产生嵌套备份。
- **位置**：`src-tauri/src/commands/md_scanner.rs` 递归扫描（`scan_md_files`，约 L104-174）无目录名排除；备份目录名定义在 `src/composables/md-rescue/useFileBackup.ts` L140/L301（字符串 `.picnexus-backup`）。
- **修法**：Rust 递归时跳过名为 `.picnexus-backup` 的目录。目录名在 Rust 与 TS 各写一份，评估登记进 `scripts/check-cross-language-constants.mjs` 的 `PAIRS`（AGENTS.md 规范针对用户可见文案，目录名属跨语言常量，登记可防漂移）。
- **验收**：Rust 单测：目录树含 `.picnexus-backup/xx.md` → 扫描结果不含；手测：修复过的文件夹再扫一次，结果不含备份文件。

### 1.3 非 UTF-8 文件拒绝写回【中】

- **问题（大白话）**：GBK 编码的 md 单文件拖入修复后，中文被静默写成 `�` 乱码，界面还报"修复成功"。（Rust 文件夹路径 `read_to_string` 遇非 UTF-8 会报错跳过，受保护；只有 JS 读写链路会损坏。）
- **位置**：`src/composables/md-rescue/useFileBackup.ts` 的 `readTextFile`（约 L150）→ `writeTextFile`（约 L173）。plugin-fs 的 `readTextFile` 用非 fatal `TextDecoder`，有损解码不报错。
- **修法**：改用 `readFile`（raw bytes）+ `new TextDecoder('utf-8', { fatal: true })` 解码；解码抛错则该文件标记"编码不受支持（非 UTF-8）"，进 failedFiles 跳过修复，不写回。加载扫描侧（`useMdFileLoader.ts`）如同样用 `readTextFile`，一并处理。
- **顺手项（可选）**：读入时记录 UTF-8 BOM，写回时补回（当前 BOM 被静默剥除）。
- **验收**：单测：GBK 字节序列 → 拒绝并报编码错误；手测：记事本 ANSI 编码含中文的 md 拖入修复 → 应提示失败而非乱码写回。

**批次 1 文档同步**：更新 `docs/flows/md-rescue-flow.md` 排查表（乱码一行改为"已拦截：非 UTF-8 文件会提示编码不受支持"；新增备份目录排除说明）。

## 批次 2：链接检测正确性（P1，防误导用户删活链/丢结果）

### 2.1 监听 `history-deleted`，清掉幽灵行【中】

- **问题（大白话）**：别的页面删了图，链接检测页 5 分钟内还显示它、还计入统计、检测还白发请求。配套函数写了却没人调用（接线没接完）。
- **位置**：`src/composables/link-check/useLinkCheck.ts` 的 `onCacheEvent`（约 L131-146，现只处理 `history-cleared`/`history-updated`）；已有现成函数 `removeRowsByHistoryIds`（约 L940，当前全仓库零调用）。
- **修法**：`onCacheEvent` 增加 `history-deleted` 分支，调用 `removeRowsByHistoryIds(p.ids)`；参照 `useTimelineDayPagination.ts` 等四个已正确监听的模块确认事件 payload 形状。确认统计/筛选是否随 rows 响应式自动更新。
- **验收**：单测：发 `history-deleted` 事件 → 对应行从 `checkRows` 消失、统计减少；手测：历史页删 2 张图 → 立即切链接检测页 → 行已消失。

### 2.2 取消后快速续检不再丢弃旧批次结果【中】

- **问题（大白话）**：大批量检测中点取消，toast 引导你"继续检测"；但旧批次的在途请求几十秒后才返回，此时新批次已开、会话号已变，旧批次已完成的几千条结果被整体丢弃、不写库，重启后全部回退"未检测"。
- **位置**：`src/composables/link-check/useLinkCheck.ts`——`cancelCheck`（约 L483-501）、`latestStartedBatchSession` 守卫（约 L383-386 与 L660-663，守卫连 `persistResultOrRollback` 一起跳过）。
- **修法**（方向，执行者先通读这两段再定）：会话守卫只拦"UI 状态推进/进度更新"，**不拦结果落库**——旧批次结果到达时仍写 DB（数据是真实检测结果，写库无害），仅当该行同时也在新批次中时不回填 UI。注意与 `applyRecentResults` 的就地 patch 保持一致，避免 UI/DB 再次分叉。
- **验收**：手测：上千条全量检测 → 中途取消 → 5 秒内点"仅未检测"续检 → 两批结束后重启 → 取消前已完成的那批仍是"已检测"。若能构造单测（mock invoke 延迟返回）更佳。

### 2.3 3xx 重定向单独归类，不再误判"失效"【中】

- **问题（大白话）**：图床返回 301/302 跳转时浏览器能正常看图，检测却标红"失效"；用户据此批量删除会误删活链接。（不跟随重定向是防 SSRF 的刻意设计，保持不变，只改归类与提示。）
- **位置**：`src-tauri/src/commands/link_checker.rs`——`redirect::Policy::none`（约 L309-314，保持）；`classify_error`（约 L79-114，3xx 落入兜底 `network`，测试 `classify_error_3xx_falls_through_to_default` 自认了该行为）。前端消费端：`useCheckFilter.ts`（invalid tab）、`useCheckStats.ts`、`useLinkStatusDisplay.ts`（tooltip）、`linkCheckPersistence.ts`（CSV）。
- **修法**：`classify_error` 对 3xx 单独返回 `redirect` 类错误型，比照现有 403 防盗链的 `browser_might_work` 出口给"浏览器可能可访问"提示；前端各消费端把 `redirect` 归入"疑似"而非"失效"（或单独 chip，执行时看现有 tab 结构取最小改动）。错误文案若 Rust/前端各一份，登记 `check-cross-language-constants.mjs`。
- **验收**：更新 Rust 测试 `classify_error_3xx_*` 的预期并通过；手测：一条 301 跳转的图片 URL → 显示"疑似/跳转"而非"失效"，tooltip 有提示。

**批次 2 文档同步**：更新 `docs/flows/link-check-flow.md`（3xx 归类说明、排查表；顺带修正文档漂移：默认筛选实为 `'invalid'` 而非 `null`）。

## 批次 3：批量迁移一致性（P1，两处都有现成模式可抄）

### 3.1 迁移落库后广播刷新事件【中，改动极小】

- **问题（大白话）**：迁移完 100 张图，历史表格"备份数"、灯箱链接菜单、时间轴候选全看不到新备份，要等重启。违反 `docs/flows/mirror-fallback-flow.md` 明文不变量（"先写 DB，再经 emitHistoryUpdated 让视图重查"）。
- **位置**：`src/composables/batchMigrate/migrateCore.ts` L262 `historyDB.update` 后无事件；`src/composables/useBatchMigrate.ts` 收尾 `finalizeResult`（约 L521-542）同样缺失；`retryFailed.ts`（约 L214）同。**正确范例**：`RetryService.ts` 约 L387-388。
- **修法**：照抄 RetryService 模式。建议按 chunk 或在收尾统一 `emitHistoryUpdated(成功 ids)` + `invalidateCache()`，避免每条各发一次事件刷爆视图（执行者看 RetryService 的粒度决定）。`retryFailed.ts` 一并补。
- **验收**：手测：迁移 3-5 张到新图床 → 不重启切历史表格/灯箱 → 新备份立即可见。

### 3.2 落库前重读最新记录，消除长窗口读-改-写竞态【中】

- **问题（大白话）**：迁移用的是 chunk 开头（可能几分钟前）取的旧快照做合并写回；期间你在灯箱删掉的失效镜像会被旧快照"复活"。
- **位置**：`src/composables/useBatchMigrate.ts` 约 L414（每 chunk 取 100 条完整 item）→ `migrateCore.ts` 约 L246-262（以陈旧 `item.results` 为 base 追加后整列覆写）。
- **修法**：`migrateCore` 在 `historyDB.update` 前用 `historyDB.getById(item.id)` 重读最新 `results`/`linkCheckStatus`/`linkCheckSummary` 作为合并 base，再 append 新结果。窗口从"分钟级"缩到"毫秒级"（彻底消除需 DB 层原子合并，成本不成比例，暂不做——已列暂缓清单）。
- **验收**：单测：mock 并发 `removeMirror` 后迁移落库 → 被删镜像不复活；手测：≥100 张迁移中，灯箱删除在途图片的一个镜像 → 迁移结束后该镜像不重现。

**批次 3 文档同步**：`docs/flows/batch-migrate-flow.md` 图 4 已与实现脱节（`skipOffset`/`processedIds` 分页已被 keyset 游标流水线替换），本批顺带重绘该图与排查表。

## 批次 4：S3 上传链路（P2，影响 6 个图床：阿里云/腾讯/七牛/又拍云/R2/自定义 S3）

### 4.1 `put_object` 设置 Content-Type【中】

- **问题（大白话）**：上传没带文件类型，图片以"二进制文件"存进桶，浏览器直开链接可能变成下载而不是显图。
- **位置**：`src-tauri/src/commands/s3_compatible.rs` L143-148（`put_object` 链上无 `.content_type()`，已亲核）。
- **修法**：按扩展名映射 MIME（png/jpg/jpeg/webp/gif/svg/avif/bmp/ico 足够，或用 `mime_guess` crate——引入前查文档），`put_object().content_type(...)`。未知扩展名回退 `application/octet-stream`。
- **验收**：cargo 单测映射函数；手测：传一张 png → 浏览器直开返回的 URL 应显示图片；用 `curl -I` 看响应头 `Content-Type: image/png`。

### 4.2 对象名唯一化，消除同名覆盖【中，含一个需用户拍板的决策】

- **问题（大白话）**：S3 对象名 = 配置路径 + 原始文件名（`src/uploaders/s3/BaseS3Uploader.ts` L78-82，已亲核），整条链路无改名逻辑；两次上传同名文件，第二张顶掉第一张，第一条历史记录的链接从此指向第二张图。
- **推荐方案（默认执行此项，用户有异议再改）**：key 增加日期+短随机段，如 `{path}/{yyyyMMdd}_{4位随机}_{原文件名}`——保留原名可读性、保证唯一、纯前端改 `BaseS3Uploader.upload` 一处。备选方案（不推荐）：上传前 `head_object` 探测冲突，多一次请求且并发仍可撞。
- **影响说明**：只影响**新上传**的 URL 结构，旧记录不受影响。
- **验收**：单测 `BaseS3Uploader` key 生成（两次同名不同 key）；手测：同名不同内容的两张图连传 → 两条历史记录链接各指各的图。

**批次 4 收尾**：改动覆盖全部 S3 系图床，真机实测至少 2 个（建议阿里云 + 自定义 S3）。
