## 批次 2：链接检测（`be0ba3b` / `a375d29` / `a88c500`）

### 2.2 取消后续检不丢结果（2026-08-21 过）

取消时「超时 6 / 未检测 22」→ 续检至 0 → 重启应用后「未检测」仍为 0，结果没丢。

**造场景比判据本身还费劲，记下来免得重来：**

- 原判据写「上千条」，实际库里只有 18 条、秒结束根本来不及点取消。
- 第一版方案「传 15 张到 dufs 再停掉 dufs」当时也不行：局域网 HTTP 会被
  `validate_probe_url` **同步判成「拦截」**，压根不发请求，停不停服务毫无区别
  （2026-08-21 起探测已放行局域网，这条限制不复存在，但黑洞服务器仍是造超时的最稳做法）。
- 最终做法：`blackhole-server.js` 当公开域名，每条卡满 10 秒超时，15 条约 20 秒才够操作。

### 2.3 3xx 不再误判失效（2026-08-20 过）

本机 301 跳转服务当公开域名，实测：徽章 `301` + 紫色「跳转」标签，
tooltip「跳转链接 (301) · 浏览器会自动跟随，通常可正常显示；检测器出于安全不跟随」。
**不是**「失效」，也没写成「防盗链限制」。

- 原判据写的「落在『疑似』tab」已过期：界面现在是独立的「跳转」标签、归在「问题」下。
- 复现脚本当时必须绑回环：旧版 `validate_probe_url` 把局域网 HTTP 判成「策略拦截」。
  该缺陷 2026-08-21 已修——探测判据对齐了上传/渲染/CSP 三处，局域网字面量与已确认主机名
  放行，脚本绑局域网 IP 也可以了。经过见
  [lightbox-gate-and-upyun-dual-chain-2026-08-20.md](./lightbox-gate-and-upyun-dual-chain-2026-08-20.md)
  的「链接检测拦掉所有局域网图床」小节。

## 批次 4：S3 上传链路

改动覆盖全部 6 个 S3 系图床（阿里云 / 腾讯 / 七牛 / 又拍云 / R2 / 自定义 S3），走**同一条**

> ⚠️ 4.1 有**两条链路**要各测一次：2026-08-13 的修复只覆盖桌面 GUI 走的
> `upload_to_s3_compatible`；编辑器 / CLI / 本地 server 走 `server/upload_handler.rs::s3_put_object`，
> 它一直没带 Content-Type，直到 issue #4 才被发现并补上。只测 GUI 会漏掉一半。

### 4.1a Content-Type · GUI 链路（2026-08-20 过）

应用里传 `.png` → 浏览器直开链接显图（不弹下载框），`curl -I` 返回 `Content-Type: image/png`。
⚠️ 必须用**新传**的图测：改动前上传的旧对象类型已写进桶里，不重传不会变
（补救见 [s3-legacy-content-type.md](../reference/troubleshooting/s3-legacy-content-type.md)）。

### 4.1b Content-Type · 编辑器/CLI 链路（2026-08-20 过）

CLI 传 `.png` 到同一个桶，返回 `image/png`。这条链路在 2026-08-18 之前**必然**返回
`application/octet-stream`，所以它同时也是「修复是否真的生效」的判据——不是走过场。

### 4.2 同名不覆盖（2026-08-20 过）

两张内容不同但都叫 `test.png` 的图（一红一蓝）连传两次：历史里两条记录的链接各指各的图，
桶里两个不同对象，名字形如 `20260813_a3f9_test.png`。改动前第一条记录的链接也会显示成第二张图。

### 4.2 反向判据：路径前缀仍生效（2026-08-20 随 U3 一并过）

配置存储路径 `images` 时上传：对象落在 `images/` 下，不在桶根目录，key 不以 `/` 开头、
没有多出一层空目录。
