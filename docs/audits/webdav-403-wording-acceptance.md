## 本轮发现：漂移已经真实发生了

审查只指出「注释说 403 是没权限，映射却说认证失败」。复核时发现更硬的证据：
**正确文案早就在仓库里，只是在另一条路上**。

`backupSyncUtils.ts` 的状态码表里一直写着 `'403': '访问被拒绝，权限不足'`。也就是说同一个 403：

| 用户走哪条路 | 改动前看到的话 |
|-------------|--------------|
| 同步过程中的 PUT/GET | 访问被拒绝，权限不足 |
| 备份的「测试连接」 | 认证失败，请检查用户名和密码 |
| 图床三条链路 | 认证失败，请检查用户名和密码 |

共用 `describe_status` 的全部意义就是消灭这种分叉，而 403 这一支恰恰漏网了。
本轮把三处统一到 `WEBDAV_FORBIDDEN_MESSAGE`，并登记进跨语言门禁。

> ⚠️ 门禁只比对**常量字面量**，不检查 `401 | 403` 这类**映射逻辑**。
> 也就是说：如果只改 Rust 侧的分支而不动前端，lint 拦不住。这一层仍然由两侧单测守着
> （`status_403_points_at_permissions_not_password` 与 `webdav.spec.ts` 的两条 403 用例）。

## 验收明细

配置：服务器 URL `http://127.0.0.1:50xx/dav`，用户名密码随便填（夹具一律拒绝）。
回环地址在 `url_policy.rs` 与 `networkPolicy.ts` 两侧都直接放行，**无需局域网 HTTP 逃生舱**。

| # | 端口 | 服务端形态 | 判据 | 结果 |
|---|------|-----------|------|------|
| 1 | 5011 | 401，只给 Digest | 服务端要求 Digest 认证 | ✅ |
| 2 | 5012 | 401，只给 Basic | 认证失败，请检查用户名和密码 | ✅ |
| 3 | 5013 | 401，两条同名 header，Digest 在前 | 认证失败，请检查用户名和密码 | ✅ |
| 4 | 5014 | 401，realm 里带逗号 | 服务端要求 Digest 认证 | ✅ |
| 5 | 5015 | **403，且带 Digest challenge** | **访问被拒绝，请检查账号对该路径的读写权限** | ✅ 截图存档 |
| 6 | 5015 | 同上，改从**图床**入口测 | 冒号后与 #5 一字不差 | ✅ |

**证据强度说明**（免得日后误读这张表）：#5 与 toast 标题有截图；#1~#4、#6 是用户逐个点击后未报告任何不符。
每次点击都在夹具日志里留下了对应端口的请求记录，请求确实到达是硬证据，**显示的文案由用户在 GUI 确认**。

5015 一个场景挡两种退化，这也是它**故意带 Digest challenge** 的原因：

- 若显示「服务端要求 Digest 认证」→ 说明 403 去读了不该读的 `WWW-Authenticate`
- 若显示「认证失败，请检查用户名和密码」→ 说明 403 又并回了 401

两个入口分别验，是因为它们是**两个 Rust 函数**（`probe_webdav_connection` / `test_webdav_storage`），
只是共用同一个 `describe_status`。夹具日志能把它们区分开：备份只打 `config.url`（`/dav`），
图床会拼上远程路径（本次是 `/dav/pics`）。

> 📌 403 场景下两个入口**都只发一次 PROPFIND**——图床测试第一步也是 PROPFIND，
> 403 会让它在那一步就早退，走不到 MKCOL/PUT。所以靠 HTTP 方法分不出入口，只能靠路径。

## 顺带修掉的既有缺陷：toast 标题与正文打架

截图暴露的问题：弹窗标题是「验证失败」，正文是「访问被拒绝，请检查账号对该路径的读写权限」。
标题在大字号红色的位置先给了个相反结论，把用户支回去改本来没错的密码——**正文刚修好的坑，标题又挖了一遍**。

`TOAST_MESSAGES.auth.failed` 的标题改为「连接失败」。它只有 3 个调用方，全是备份 WebDAV 的
「测试连接」（`SettingsView.vue:242/251/283`），不波及其他图床。改完后与图床侧的
`auth.connectionFailed` 标题一致，同一个故障在两个入口不再说两种话。
